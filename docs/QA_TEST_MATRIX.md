## How to read this matrix

**Result**

| Result | Meaning |
|---|---|
| **PASS** | Behaviour confirmed. Either a named automated test is green in the 2026-10-07 run, or the behaviour is fully determined by the cited code and was read there. The Evidence column says which (`Auto:` or `Code:`). |
| **FAIL** | Observed to fail. See the summary below for any rows in this state. |
| **WARNING** | It works today, but a known weakness exists that will bite under a stated condition. Not a pass, not a defect. |
| **UNVERIFIED** | No evidence either way. The Test steps column gives the exact manual procedure. Nobody should read this as "probably fine". |
| **NOT APPLICABLE** | Absent from this release by design. |

**Severity if failed**: *Critical* = blocks release or App Review, or is a privacy, legal or data-loss failure. *High* = a core journey is broken for a meaningful share of users. *Medium* = degraded, with a workaround. *Low* = cosmetic or rare.

**Evidence tags**: `Auto:` a named automated test (file and line). `Code:` read at file and line. `Live:` probed against the live service on 2026-10-07. `None` means nothing exists beyond the manual steps.

**What the automated tests do and do not reach.** Unit tests run against in-memory fake backends. The seeded UI tests (`-uiTestSeed`) build a container with no backend at all, so no test can reach production Supabase. The one UI test that does, `DemoWalkthroughTests.testDemoWalkthrough`, signs in to production and is red without QA credentials (see "Known failures" below). Consequently every row that says "live" or "production" is a manual row, and "Auto:" on a sign-in row means the client logic is proved, not the server.

**Manual-test conventions.** "Device" means a physical iPhone running the TestFlight build 31 binary. "Throwaway account" means an address you control and can discard. **Never use the App Review account for destructive or state-changing steps**; it is shown below only as `[REVIEW DEMO EMAIL]` and `[REVIEW DEMO PASSWORD]`, and no credential value appears anywhere in this repository's documents.

## How to run the automated suites

The iPhone 17 family is what exists on the reference machine (iPhone 17, 17 Pro, 17 Pro Max, 17e, iPhone Air; iOS 26.5 runtime). A destination naming an iPhone 15 or 16 fails with "Unable to find a device matching". Never use "Any iOS Simulator Device". Check with `xcrun simctl list devices available`.

```bash
cd /Users/lucasvalenca_sf/genesxy_apple.V1.02

# 1. Core (domain) suite. Runs on macOS, no simulator, 314 tests.
swift test

# 2. App unit suite, 405 tests, about 45 seconds once built.
#    The target is GenesyxAppTests. The sources live in App/GenesyxTests/, but
#    -only-testing:GenesyxTests is rejected (exit 70, "isn't a member of the specified test plan or scheme").
xcodebuild test -project Genesyx.xcodeproj -scheme Genesyx \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  -only-testing:GenesyxAppTests

# 3. UI suite, about 23 minutes. Run it on iPhone 17 AND on iPhone 17e.
#    env -u stops the production walkthrough from ever signing in.
env -u DEMO_PASSWORD -u DEMO_EMAIL xcodebuild test -project Genesyx.xcodeproj -scheme Genesyx \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  -only-testing:GenesyxUITests
#    Repeat with name=iPhone 17e.

# 4. One UI test, addressed as Target/Class/method.
xcodebuild test -project Genesyx.xcodeproj -scheme Genesyx \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  -only-testing:GenesyxUITests/AuthGateUITests/testMandatorySignInOffersPasswordRecovery

# 5. Reset notification permission so the opt-in test (row I6) is not skipped.
xcrun simctl uninstall booted com.genesyx.app

# 6. Run from a clean export when a failure might be your own working tree.
D=$(mktemp -d) && git archive HEAD | tar -x -C "$D" && cd "$D"
#    then add: -derivedDataPath "$D/dd" -onlyUsePackageVersionsFromResolvedFile
```

Things that catch people:

- **Cmd-U and a bare `xcodebuild test` run the UI suite too**, because the `Genesyx` scheme's test action lists both bundles (`project.yml:185-188`). For a quick loop use `-only-testing:GenesyxAppTests`.
- **Supplying `DEMO_PASSWORD` runs `testDemoWalkthrough` against production.** It edits the demo account and restores each change inline (`DemoWalkthroughTests.swift:3-18`). Use `DEMO_EMAIL` to point it at a separate QA account; never the App Review account, and never put either value in the repository, CI logs or shell history.
- **Seeded UI tests are offline and wipe app data on every launch.** They cannot reach Supabase by construction.
- **A green suite does not prove the app builds for release.** Every test target is a Debug build. Build 18 was unarchivable for days while hundreds of tests passed (an `#if DEBUG` around an import; the comment survives at `AppContainer.swift:2-5`). The release checklist compiles Release before anything is called ready.
- **Leave simulators as you found them.** A falsification build left installed reads as a regression to the next person.
- Debug-only launch arguments for poking at a state by hand: `-uiTestSeed YES`, `-uiTestSignedOut YES`, `-uiTestOnboarding YES`, `-uiTestTab <0-6>`, `-uiTestKeepStore YES`.

## Findings raised while building this matrix

None of these is a release blocker on its own. Each is listed so it is not lost.

1. **I11, new:** `testSignOutDoesNotBlankMedicalSources` fails reproducibly because of iOS's "Save Password?" sheet. Test fix needed.
2. **L3:** Log out discards entries that have not yet synced, silently. It is deliberate for a shared phone but unannounced; a user who logs out offline loses her last entries.
3. **E9:** Sign in with Apple revocation is handled only through the running-app notification. No launch-time `getCredentialState` check exists; a revocation made while the app was not running may leave her signed in.
4. **B13:** the upload of the consent trail to `consent_events` has no automated test (no test fakes `ConsentBackend`). Consent is the one thing both Apple Review and a regulator would look for.
5. **L2:** the live `app_config` table does not exist, so the forced-update gate can never fire and every launch makes one wasted request.
6. **L4:** signing in while offline tells her to check her details.
7. **G17 and K7:** the medical sources test is named "AllEleven" for a list that now holds 18 and checks only the first and thirteenth row; `efsa-water` and two NHS links need a look in a browser.
8. **H8 and H9:** the two sync weaknesses (rows stuck behind a 5xx or 429 with no backoff; the unbounded list queries) are real code paths, not yet reachable by data volume. Fix H9 and H10 together.

**Do not "fix" the Supabase advisor warnings blindly.** `join_waitlist` being callable by `anon` is almost certainly intentional (the public waitlist form); the gap is a missing captcha or rate limit, not the grant. `delete_current_user()` callable by `authenticated` is the Android deletion path, so revoking it breaks GDPR deletion on Android. `waitlist_emails` having RLS with no policies is correct, because it also has no grants.
